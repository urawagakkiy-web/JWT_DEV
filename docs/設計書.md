## 1. 目的とスコープ

ログインしたユーザーが、自分の物件情報を登録・閲覧・編集・削除できるWebアプリ。
Supabase の認証と行レベルセキュリティ（RLS）を使い、**他人の物件は取得すらできない**構成にする。

### スコープ内

- メールアドレス＋パスワードによる会員登録・ログイン・ログアウト
- 物件の CRUD（物件名・家賃・エリア・間取り）
- 未ログイン時のアクセス制御

### スコープ外（今回は作らない）

- 物件の検索・並べ替え・絞り込み、画像の登録、複数ユーザーでの共有
- パスワード再設定、SNSログイン、メールアドレス変更
- 管理者機能、物件の公開・非公開の区別

## 2. システム構成

```
  ブラウザ（React SPA）
        │
        │ ①静的ファイルの配信（HTML / JS / CSS）
        ▼
  Vercel（ホスティング）
        │
        │ ※ビルド時に VITE_ 環境変数を JS に埋め込む
        ▼
  ビルド成果物 dist/
        │
        │ ②認証・データ操作（HTTPS / REST）
        ▼
  Supabase
    ├── Auth（ユーザー登録・ログイン・JWT発行）
    └── PostgreSQL（properties テーブル ＋ RLS）
```

サーバーサイドのコードは持たない。ブラウザから Supabase を直接呼ぶ構成のため、
**アクセス制御はアプリ側ではなくデータベース側（RLS）で担保する**のが本設計の要点。

## 5. データ設計

### 5.1 テーブル定義（`public.properties`）

| 列 | 型 | 制約 | 内容 |
|---|---|---|---|
| `id` | uuid | PK, default `gen_random_uuid()` | 物件ID |
| `user_id` | uuid | NOT NULL, default `auth.uid()`, FK → `auth.users(id)` ON DELETE CASCADE | 登録者 |
| `name` | text | NOT NULL, 空文字禁止 | 物件名 |
| `rent` | integer | NOT NULL, 0以上 | 家賃（円） |
| `area` | text | NOT NULL, 空文字禁止 | エリア名 |
| `layout` | text | NOT NULL, 空文字禁止 | 間取り（例: 1LDK） |
| `created_at` | timestamptz | NOT NULL, default `now()` | 登録日時 |
| `updated_at` | timestamptz | NOT NULL, default `now()` | 更新日時（トリガーで自動更新） |

索引: `(user_id, created_at desc)` — 一覧の取得順に合わせたもの。

### 5.2 設計上の判断

- **`user_id` の既定値を `auth.uid()` にした。**
  アプリから登録者を送らなくてよくなり、値を詐称される経路が1つ減る
- **家賃は `integer`（円）。** 小数を扱わないため。通貨計算で `float` は使わない
- **`updated_at` はトリガーで更新。** アプリ側の書き忘れを防ぐ
- **ユーザー削除時は物件も削除（CASCADE）。** 参照先の無い行を残さない

## 6. セキュリティ設計

### 6.1 認証

Supabase Auth のメール＋パスワード認証。ログイン成功時に JWT が発行され、
`@supabase/supabase-js` が `localStorage` に保存して自動で更新する。
以降のDBアクセスにはこの JWT が付与され、DB 側は `auth.uid()` でユーザーを判別する。

現在のプロジェクト設定は `mailer_autoconfirm: true`（確認メール省略）。
オンにした場合も動作するよう、登録直後に session が返らないケースを実装側で分岐している。

### 6.2 RLS ポリシー

`properties` テーブルで RLS を有効化し、4操作すべてにポリシーを設定する。

| 操作 | 条件 |
|---|---|
| SELECT | `using (auth.uid() = user_id)` |
| INSERT | `with check (auth.uid() = user_id)` |
| UPDATE | `using (auth.uid() = user_id)` ＋ `with check (auth.uid() = user_id)` |
| DELETE | `using (auth.uid() = user_id)` |

**UPDATE に `with check` を併記しているのが要点。**
`using` は「どの行を更新できるか」、`with check` は「更新後の行が満たすべき条件」を指す。
`using` だけだと、自分の行の `user_id` を他人のIDに書き換えて所有権を移せてしまう。

RLS が絞り込むため、**アプリ側のクエリに `.eq("user_id", ...)` は書かない。**
書くと同じルールが2か所に散り、DB 側を直したときに食い違いが起きる。

### 6.3 キーの扱い

| キー | 置き場所 | 備考 |
|---|---|---|
| Publishable key | `.env` → ビルドで JS に埋め込み | 公開前提のキー。RLS があるため単体では何もできない |
| service_role key | **使わない** | RLS を無視できる。ブラウザに配布してはならない |

`.env` は `.gitignore` で除外し、リポジトリに含めない。
本番の値は Vercel のダッシュボードで設定する（`vercel.json` には書かない）。

## 7. 機能設計

### 7.1 認証状態の管理

`AuthProvider` がアプリ全体を包み、以下を担う。

1. 起動時に `supabase.auth.getSession()` で保存済みセッションを復元する
2. `supabase.auth.onAuthStateChange()` を購読し、ログイン・ログアウト・トークン更新を反映する
3. 復元が終わるまで `loading = true` を保つ

`ProtectedRoute` は `loading` 中は判定を保留する。
**保留しないと、ログイン済みでも復元完了前に未ログインと判定され、一瞬ログイン画面が出る。**

### 7.2 CRUD の流れ

| 操作 | 呼び出し | 画面の更新 |
|---|---|---|
| 一覧 | `select(...).order("created_at", desc)` | 取得結果で置き換え |
| 登録 | `insert(...).select().single()` | 返った行を先頭に追加 |
| 更新 | `update(...).eq("id", id).select().single()` | 該当1件を差し替え |
| 削除 | `delete().eq("id", id)` | 該当1件を除外 |

登録・更新は**返ってきた行で画面を更新する**（再取得しない）。
サーバーが確定した値（`id`・`created_at`）をそのまま使え、通信も1往復で済むため。

削除は取り消せないため、`window.confirm` で確認する。
通信中は `busy` フラグで各ボタンを無効化し、二重操作を防ぐ。

### 7.3 モジュール構成

| ファイル | 責務 |
|---|---|
| `src/main.jsx` | 起動 |
| `src/App.jsx` | ルーティング定義 |
| `src/supabaseClient.js` | クライアント生成、`.env` の不備検出 |
| `src/api/properties.js` | 物件のCRUD。画面から Supabase の作法を隠す |
| `src/api/dbError.js` | DBエラーの日本語化 |
| `src/authError.js` | 認証エラーの日本語化 |
| `src/format.js` | 家賃の表示整形 |

| `src/components/ProtectedRoute.jsx` | 未ログイン時のリダイレクト |

## 8. エラー処理設計

Supabase が返すエラーは英語のため、利用者に見せる前に日本語へ変換する。
該当しないものは原文をそのまま表示し、原因を追えるようにする。

| 状況 | 表示 |
|---|---|
| 認証情報の誤り | メールアドレスまたはパスワードが違います。 |
| 登録済みのメール | このメールアドレスはすでに登録されています。 |
| テーブル未作成（`PGRST205` / `42P01`） | 物件テーブルがまだありません。schema.sql を実行してください。 |
| RLS で拒否（`42501` / `PGRST301`） | 権限がないため操作できませんでした。 |
| CHECK 制約違反（`23514`） | 入力内容が正しくありません。 |
| 通信失敗（`Failed to fetch`） | 接続できません＋原因の候補4つ |
| `.env` 未設定 | 送信せずに、不備の内容を表示 |

**設定不備は通信前に検出して止める。** 存在しないホストへ通信すると、
原因が「ネットワーク障害」に見えてしまい、切り分けに時間がかかるため。

## 9. 非機能

| 項目 | 方針 |
|---|---|
| 対応ブラウザ | モダンブラウザ（ES Modules 対応） |
| レスポンシブ | 375px 幅で横スクロールが出ないこと |
| 操作性 | ボタンの高さは 44〜48px 以上を確保 |
| 色 | 状態は色だけでなく記号（`×` `○`）でも示す |
| テーマ | `:root` の CSS 変数だけで決まる。個々のセレクタに色を直書きしない |
| 件数 | 表示件数をハードコードしない。データから算出する |

自動テストは無い。確認はブラウザでの実操作で行う。
